# Wazuh Custom Rules

This directory contains Wazuh custom rules generated by SentinelForge from Sigma
source rules. These files are generated artifacts and should not be edited
manually.

## Generation

Rules are generated by running the conversion pipeline:

```bash
sentinelforge convert --backend wazuh
```

Or using the script directly:

```bash
python scripts/convert_rules.py
```

## Rule ID Allocation

Custom rules use the Wazuh reserved range **100000-199999**. SentinelForge
allocates identifiers deterministically from the SHA-256 hash of each rule's
UUID, ensuring stable IDs across runs.

## File Naming

Generated files follow the pattern:
```
{slugified-title}-{uuid-prefix}.xml
```

Example: `ssh-authentication-failure-a1b2c3d4.xml`

## Deployment

Copy the generated XML files to your Wazuh manager's custom rules directory:

```bash
# On the Wazuh manager
cp wazuh/rules/*.xml /var/ossec/etc/rules/
```

Then restart the Wazuh manager:

```bash
systemctl restart wazuh-manager
```

## Testing

Test generated rules with `wazuh-logtest`:

```bash
/var/ossec/bin/wazuh-logtest -c wazuh/rules/ssh-authentication-failure-a1b2c3d4.xml
```

Paste a test log event when prompted.

## Rule Groups

Generated rules are tagged with groups based on their platform and log source:
- `linux`, `windows`, `common` - Platform
- `sshd`, `auditd`, `cron` - Linux services
- `security`, `system`, `powershell` - Windows services
- `authentication`, `persistence`, `execution`, `audit` - MITRE tactics

## MITRE ATT&CK Metadata

Rules include MITRE ATT&CK metadata when available in the source Sigma rule:

```xml
<mitre id="T1110" tactic="Credential Access" technique="Brute Force"/>
```

## Important Notes

1. **Do not edit generated files directly** - Changes will be overwritten on
   next conversion. Modify the source Sigma rules in `rules/` instead.

2. **Correlation rules are not converted** - Rules requiring multi-event
   correlation with time windows (marked as `kind: correlation` or using
   unsupported Sigma features) are rejected during conversion.

3. **Field mappings are required** - Every Sigma field used in a converted
   rule must have a corresponding Wazuh field mapping in the configuration.

4. **Decoder compatibility** - Generated rules assume standard Wazuh decoders
   (sshd, auditd, windows, etc.). Custom decoders may require mapping overrides.
